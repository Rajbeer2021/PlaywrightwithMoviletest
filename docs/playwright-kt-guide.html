Playwright KT Guide

OrangeHRM Automation Framework

This framework follows a scalable Playwright test architecture using project-root fixtures, a page object model, GitHub Actions execution, BrowserStack cloud runs, and a central reports layer for dashboards and artifacts.

Current Framework Architecture

Local

Project Structure

The framework has a clean root-level separation between test logic, reusable fixtures, page objects, and reports.

  • fixtures/ contains shared Playwright setup
  • pages/ contains page-specific selectors and actions
  • reports/ stores HTML dashboards, screenshots, results, logs

Page Object Model (POM)

Why it matters

Instead of writing selectors in each test, locators are centralized inside page classes. This makes the framework scalable, readable, and easier to maintain.

  • One locator change updates all related tests
  • Test cases become scenario-focused
  • Better collaboration and reuse across suites

Example structure

pages/
  LoginPage.js
  DashboardPage.js

fixtures/
  test.js

tests/
  orangehrm.spec.js
  hrmtest2.spec.js
3

Fixture Layer and Reusability

The root-level fixture file is the single source for Playwright setup. It chooses the environment target and exposes the shared test and expect objects for all test files. This keeps configuration logic centralized instead of copied repeatedly. 

const target = (process.env.BROWSER_TARGET || 'desktop').toLowerCase();

switch (target) {
  case 'desktop':
    ({ test, expect } = require('@playwright/test'));
    break;
  case 'android':
    ({ test, expect } = require('./android-test'));
    break;
}
4

Current Flow in Practice

  1. Developer writes a test using page objects.
  2. Fixture file gives browser and environment setup.
  3. Playwright executes the suite locally or in CI.
  4. Results go to the central reports/ folder.
  5. A custom HTML dashboard is generated and optionally published to GitHub Pages.
  6. Workflow artifacts are uploaded and accessible from GitHub Actions.

Advantages of the Current Implementation

Maintainability

Selectors are stored in page objects rather than spread across tests, making updates faster and less risky.

Scalability

More pages and suites can be added without rewriting the same UI locator logic.

CI Reliability

GitHub Actions workflows run only the relevant suites and publish dashboards after successful execution.

Cloud Capability

BrowserStack integration is kept narrow and intentional, avoiding unnecessary OS/browser matrix noise.

Better Reporting

The same report is usable for local execution, CI dashboard review, and cloud test visibility.

Clean Team Workflow

Developers can run local checks, CI can publish the report on success, and the team can download ZIP artifacts when needed.

Single-Target BrowserStack Runner (Local PowerShell)

The project now includes a local PowerShell wrapper, run-local-browserstack.ps1, which reads the current BrowserStack credentials from browserstack.yml, rewrites the YAML for a single selected target, and runs only that OS/browser combination. This avoids accidental full-matrix execution while still validating BrowserStack behavior from the local machine. 

# Windows 11 - Chrome
.\run-local-browserstack.ps1 -Suite smoke -Target windows11-chrome

# Windows 11 - Edge
.\run-local-browserstack.ps1 -Suite sanity -Target windows11-edge

# Android 15 - Samsung Galaxy S25 Chrome
.\run-local-browserstack.ps1 -Suite regression -Target samsung-s25-chrome

# macOS 14 - Safari
.\run-local-browserstack.ps1 -Suite smoke -Target macos-14-safari

# Full matrix (only if intentionally needed)
.\run-local-browserstack.ps1 -Suite all -FullMatrix

Supported local target names include: windows11-chrome, windows10-chrome, windows11-edge, windows11-firefox, macos-14-safari, samsung-s25-chrome, samsung-s24-chrome, and pixel10-chrome.

Important: only one target is selected per run. This keeps BrowserStack execution focused, stable, and aligned with the platform currently configured in the project file.

Recommended Patterns

  • Keep all locators inside page classes under the root pages/ folder.
  • Keep browser setup and environment selection in the root fixtures/ layer.
  • Use test tags such as @smoke, @sanity, and @regression for CI targeting.
  • Keep results and screenshots under a single reports/ directory.
  • Use the local BrowserStack PowerShell runner when validating one specific OS/browser target from the local machine.
  • Use GitHub Pages for online preview and artifact ZIP for downloadable delivery.
Summary: the framework is now aligned to a proven automation model: centralized fixtures, page object structure, cloud compatibility, local BrowserStack targeting, clean CI orchestration, and a professional dashboard that is publishable online after successful execution.

Key Design Decisions

  • One BrowserStack YAML file only, to avoid accidental matrix explosion.
  • Single report root: reports/ for all artifacts.
  • Test tagging by smoke, sanity, and regression.
  • Local and cloud runs use the same test suite logic.
  • GitHub Actions workflows are manual/on-demand only.

Execution Modes

1. Local Desktop Execution

This is the default execution path for local machine validation using the standard Playwright config. 

# Smoke - headless
npx playwright test tests/orangehrm.spec.js --grep "@smoke" --config=playwright.config.js

# Smoke - headed
npx playwright test tests/orangehrm.spec.js --grep "@smoke" --config=playwright.config.js --headed

# Sanity - headless
npx playwright test tests/orangehrm.spec.js --grep "@sanity" --config=playwright.config.js

# Regression - headless
npx playwright test tests/orangehrm.spec.js --grep "@regression" --config=playwright.config.js

# Full local suite
npx playwright test tests/orangehrm.spec.js --config=playwright.config.js

2. Android Emulator Execution

The Android config runs the same test file with an Android-targeted Playwright profile. 

# Android run
npx playwright test --config=playwright.android.config.js
This config keeps the scope clean for emulator/browser-based mobile execution while allowing the same test logic to be reused.

3. BrowserStack Cloud Execution

The BrowserStack run uses the BrowserStack Node SDK and a single YAML config. This avoids unintentional multi-OS expansion. 

# BrowserStack smoke
npx browserstack-node-sdk playwright test tests/orangehrm.spec.js --grep "@smoke" -- --config=playwright.browserstack.config.js --project=windows-chrome

# BrowserStack regression
npx browserstack-node-sdk playwright test tests/orangehrm.spec.js --grep "@regression" -- --config=playwright.browserstack.config.js --project=windows-chrome

# BrowserStack sanity
npx browserstack-node-sdk playwright test tests/orangehrm.spec.js --grep "@sanity" -- --config=playwright.browserstack.config.js --project=windows-chrome

GitHub Actions / CI Flow

On-demand workflow behavior

  • Smoke workflow runs only when manually triggered.
  • Sanity workflow runs only when manually triggered.
  • Regression workflow runs only when manually triggered.
  • BrowserStack workflow runs only when manually triggered.
  • No daily cron/job runs are enabled.
# Smoke on GitHub runner
gh workflow run smoke.yml --ref main --field run_on_browserstack=false

# Smoke on BrowserStack
gh workflow run smoke.yml --ref main --field run_on_browserstack=true --field browserstack_project=windows-chrome

# Regression on GitHub
gh workflow run regression.yml --ref main --field run_target=github

# Regression on BrowserStack
gh workflow run regression.yml --ref main --field run_target=browserstack --field browserstack_project=windows-chrome

BrowserStack YAML and Cloud Execution Flow

Single-target YAML strategy

# browserstack.yml
userName: ${BROWSERSTACK_USERNAME}
accessKey: ${BROWSERSTACK_ACCESS_KEY}
framework: playwright
logDir: ./reports/log
logLevel: error

platforms:
  - os: Windows
    osVersion: "11"
    browserName: chrome
    browserVersion: latest
    playwrightConfigOptions:
      name: windows-chrome
This keeps the project stable and avoids the common issue of a YAML matrix triggering the tests across every OS/browser combination unintentionally.

Execution Best Practices

  • Use the local suite for quick validation before pushing.
  • Use smoke for release confidence and fast checks.
  • Use sanity when broader validation is needed.
  • Use regression when a full validation cycle is required.
  • Use BrowserStack only for cross-browser and OS verification.
  • Keep credentials in environment variables and never commit them to the repo.
