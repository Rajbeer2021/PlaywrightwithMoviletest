Current CI/CD flow

1. Local execution

  • Developers validate the automation locally using the root-level fixtures and page objects.
  • Tests can be filtered with tags such as @smoke, @sanity, and @regression.
  • Results are written to the common reports folder.

2. GitHub Actions orchestration

  • Workflows trigger smoke, sanity, regression, and browserstack runs on demand.
  • Node is installed, dependencies are restored, and Playwright browser dependencies are set up.
  • The project uses a single BrowserStack target instead of expanding into all OS/browser combinations.

3. BrowserStack cloud validation

  • The browserstack.yml file is intentionally narrowed to one execution target.
  • Cloud run is used for targeted compatibility validation and on-demand runs.
  • This avoids noisy matrix execution and keeps the pipeline predictable.

4. Dashboard and publishing

  • The custom HTML report is generated from the execution results and stored under reports/.
  • GitHub Pages publishes only the final successful build to the public site.
  • A ZIP artifact is also uploaded so it can be downloaded from the GitHub Actions run.
  • The dashboard root is index.html, while customreport.html is kept as the direct static file.

Why this flow is strong

Fast local feedback

  • Quick iteration before pushing code
  • No unnecessary cloud cost during development

Reliable CI

  • Workflows trigger only when required
  • Test publishing is gated on success

Cloud confidence

  • BrowserStack runs validate real environment compatibility
  • Single target keeps execution focused

Professional reporting

  • Static dashboard is easy to review online
  • Artifact ZIP helps with downloadable evidence
Recommended approach: keep local runs and browserstack runs separate but deterministic, publish the HTML report after a green build, and keep all generated artifacts in one central reports folder for easy access and traceability.
